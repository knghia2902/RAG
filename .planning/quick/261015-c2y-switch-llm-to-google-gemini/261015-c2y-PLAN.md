# Quick Plan: Switch LLM Provider to Google Gemini (gemini-flash-lite-latest)

## Threat Model (ASVS L1 Compliance)

| Threat ID | Threat Category | Scenario | Mitigation |
|---|---|---|---|
| TM-SEC-01 | Information Disclosure | GEMINI_API_KEY is exposed in logs, API responses, or error stack traces | Store key in SecretStr in Settings; ensure `/api/v1/status` only returns boolean `provider_configured`; `mask_secrets` redacts Gemini API keys |
| TM-SEC-02 | Network Exposure / Tampering | Connecting backend and worker to `web` network exposes database or message broker | Only attach `backend` and `worker` to `web` network; `postgres` and `rabbitmq` remain strictly on `local: {internal: true}`; no database ports exposed externally |
| TM-SEC-03 | Denial of Service / API Timeout | Gemini API latency spikes or hangs | GeminiLLMAdapter enforces `timeout=30.0s` via httpx.Client; GroundedGenerator catches TimeoutError and raises structured LLMTimeoutError per SYS-05 |
| TM-SEC-04 | Grounding Integrity / Hallucination | Gemini generates ungrounded claims or hallucinated incident causes | Maintain GroundedGenerator citation verification, prompt injection defense, and uncertainty/conflict detection (RAG-01, RAG-04, RAG-05) |

<objective>
Configure the backend and worker to support Google Gemini as LLM Provider using the GEMINI_API_KEY in `.env` and `gemini-flash-lite-latest` via Google's OpenAI-compatible endpoint, while keeping embeddings on `text-embedding-3-small`. Connect backend and worker to the `web` network in `docker-compose.yml` for external egress, update configuration settings and provider factories, and verify end-to-end RAG chat and incident reasoning.
</objective>
