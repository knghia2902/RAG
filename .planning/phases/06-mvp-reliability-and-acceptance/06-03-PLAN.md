# Plan 06-03: Latency Benchmarking Harness & Operational Limits Validation

<threat_model>
## Security Threat Model (ASVS L1)

| Threat ID | Category | Threat Description | Mitigation Strategy |
|-----------|----------|-------------------|---------------------|
| T-06-06 | Denial of Service (DoS) via Oversized Uploads | Người dùng tải lên tệp tài liệu quá lớn (>10MB) làm cạn kiệt bộ nhớ worker hoặc tràn đĩa đệm | Kiểm tra nghiêm ngặt `MAX_FILE_SIZE` (10MB) ngay tại tầng API trước khi lưu trữ hoặc chuyển vào hàng đợi Celery |
| T-06-07 | Hanging Requests & Resource Exhaustion | Lời gọi LLM hoặc truy vấn vector bị treo không giới hạn thời gian làm kiệt connection pool | Thiết lập `timeout = 30.0` giây trên toàn bộ các client HTTP/LLM và phản hồi lỗi HTTP 504 rõ ràng theo SYS-05 |
</threat_model>

<context>
Theo yêu cầu EVAL-03 và các quyết định D-08, D-09:
- **D-08 (Chi tiết từng khâu đo lường):** Xây dựng script `backend/scripts/benchmark_latency.py` đo lường độ trễ độc lập cho 4 khâu:
  1. *Ingestion:* Thời gian phân tích và bóc tách (parse + chunk) các định dạng PDF, DOCX, CSV, Log.
  2. *Retrieval:* Thời gian truy vấn hybrid search (lexical + pgvector cosine similarity).
  3. *Generation:* Thời gian sinh phân tích sự cố (đo trên Fake Provider và OpenAI API nếu có cờ `--live`).
  4. *PDF Generation:* Thời gian WeasyPrint biên dịch HTML sang file PDF A4 tiếng Việt nhiều trang.
  - Sử dụng `time.perf_counter()` và tính toán chính xác p50, p95 qua nhiều lần lặp (`iterations >= 5`).
- **D-09 (Xác lập và kiểm chứng giới hạn vận hành):**
  - Giới hạn kích thước file tối đa: 10MB (từ chối ngay với HTTP 413 Payload Too Large).
  - Giới hạn thời gian timeout: 30s (ngắt an toàn và trả về lỗi, không treo tiến trình).
  - Khả năng xử lý worker: kiểm tra worker duy trì ổn định dưới mức tải đồng thời (`concurrency = 2`).
</context>

- `backend/app/rag/parsers/`
- `backend/app/rag/retriever.py`
- `backend/app/modules/log_analysis/reasoner.py`
- `backend/app/modules/reports/pdf_generator.py`
</read_first>
<action>
Tạo file `backend/scripts/benchmark_latency.py`:
- Cung cấp các tham số dòng lệnh CLI qua `argparse`:
  - `--iterations`: Số lần lặp đo lường cho mỗi khâu (mặc định: 5).
  - `--live`: Chạy benchmark với OpenAI API thực tế (nếu có `OPENAI_API_KEY`). Mặc định dùng Fake Provider để chạy offline.
  - `--output`: Đường dẫn lưu báo cáo JSON kết quả (mặc định: `benchmark_results.json`).
- Đo lường từng giai đoạn bằng `time.perf_counter()`:
  - `benchmark_ingestion()`: Đo thời gian parse tệp `wms_songthan_orders.log`, `SOP-LOG-01_Xu_Ly_Loi_Dong_Bo_WMS_TMS.txt`, và `sample_tickets.csv`.
  - `benchmark_retrieval()`: Đo thời gian thực thi truy vấn hybrid retriever cho câu hỏi: "Tìm lỗi đồng bộ đơn hàng DH001".
  - `benchmark_generation()`: Đo thời gian gọi reasoning LLM tổng hợp báo cáo sự cố.
  - `benchmark_pdf_export()`: Đo thời gian WeasyPrint biên dịch báo cáo tuần mẫu thành tệp PDF.
- Tính toán phân vị:
  - Dùng `statistics.median(latencies)` cho p50.
  - Dùng `statistics.quantiles(latencies, n=100)[94]` hoặc công thức tương đương cho p95.
- Định dạng hiển thị kết quả: In bảng ASCII căn chỉnh đẹp mắt trên terminal hiển thị: Giai đoạn, Số mẫu, p50 (ms), p95 (ms), Min (ms), Max (ms).
</action>
<acceptance_criteria>
- `backend/scripts/benchmark_latency.py` tồn tại và chạy được bằng lệnh: `python backend/scripts/benchmark_latency.py --iterations 2`.
- Kết quả terminal in ra bảng số liệu rõ ràng với các cột p50 và p95 cho cả 4 khâu: Ingestion, Retrieval, Generation, PDF.

### Task 06-03-02: Operational Limits & Graceful Degradation Test Suite
<read_first>
- `backend/app/api/sources.py`
- `backend/app/api/reports.py`
- `backend/tests/acceptance/conftest.py`
</read_first>
<action>
Tạo file `backend/tests/acceptance/test_operational_limits.py`:
- `test_upload_file_size_limit_enforced`:
  - Tạo một tệp dữ liệu giả lập có kích thước 11MB (vượt quá giới hạn 10MB).
  - Gửi request `POST /api/v1/sources/upload` bằng `test_client`.
  - Xác nhận API trả về mã lỗi HTTP 413 Payload Too Large với thông báo rõ ràng về giới hạn kích thước tệp.
- `test_network_timeout_handling_sys05`:
  - Giả lập tình huống client hoặc LLM Provider bị timeout (trì hoãn phản hồi > 30s).
  - Xác nhận hệ thống ngắt kết nối an toàn, trả về lỗi HTTP 504 Gateway Timeout hoặc thông báo lỗi thân thiện, không bị treo request vô hạn và không crash container.
- `test_graceful_error_without_mock_content`:
  - Khi một dịch vụ ngoại vi gặp lỗi hoặc không khả dụng, kiểm tra rằng hệ thống hiển thị thông báo lỗi rõ ràng theo nguyên tắc SYS-05, tuyệt đối không tự bịa đặt nhận định hoặc số liệu giả để che giấu lỗi.
</action>
